# RetailPulse: what's in the codebase

## 1. What the project is
RetailPulse is a Final Year Project that turns existing CCTV footage into retail analytics. It tracks whether customers get attended to, how staff spend their time, and which zones are busy. There are two runtimes:

- **Next.js 15 / React 19 frontend** (`frontend/`): the manager and employee web app.
- **FastAPI backend** (`backend/`): store operations (SQLite), the voice agent, camera handoff and the computer-vision (CV) "interaction" pipeline.

`npm run dev:all` (`scripts/run-dev.mjs`) starts both: uvicorn on `127.0.0.1:8011` and `next dev frontend`. It prefixes their logs and kills both if either one exits. Inference runs on CPU by default; `backend/device.py` has a `USE_GPU` switch.

### Scripts (root `package.json`)
The frontend is not a separate npm package: the root `package.json`, `tsconfig.json` (path alias `@/*` → `frontend/src/*`) and `node_modules` serve `frontend/`.

| Script | What it runs |
|---|---|
| `dev` / `build` / `start` | `next dev\|build\|start frontend` with `PYTHON_BIN=./.venv/bin/python` |
| `dev:all` | `scripts/run-dev.mjs`: loads `.env*` via `@next/env`, caps Next.js heap at 768 MB (`FRONTEND_NODE_OPTIONS` overrides) |
| `lint` | ESLint with `frontend/eslint.config.mjs` |
| `backend:api` | uvicorn alone on `:8011` |

**Python setup:** one `.venv` at the repo root. `backend/requirements.txt` (OpenCV, Ultralytics, torch, FastAPI, PyAV, scipy, lap) covers everything; `backend/interaction/requirements-cv.txt` adds it plus pinned `ultralytics==8.4.135`, `openvino==2026.4.1` and `torchvision`.

**Builds ignore errors:** both `next.config.ts` files set `typescript.ignoreBuildErrors`, and `frontend/next.config.ts` also sets `eslint.ignoreDuringBuilds` (a workaround for Vercel free-tier memory). Type errors only show up in local `tsc`/editor checks.

**Env vars** (`.env.example`): `RETAILPULSE_SERVICE_URL`, `RETAILPULSE_INTERNAL_SECRET` / `POS_INTERNAL_SECRET`, `POS_AUTH_SECRET` (see gap 3), `RETAILPULSE_DB_PATH`, `RETAILPULSE_BOOTSTRAP_MANAGER_*`, `PYTHON_BIN`, `HF_*` (token, router URL, models, timeout) and `ELEVENLABS_*` (key, base URL, voice, model, output format, timeout).

## 2. How requests flow and how auth works

```
Browser ──► Next.js page ──► /api/backend/[...path] (proxy) ──► FastAPI :8011
                │                 adds x-retailpulse-internal-secret + role/user headers
                └─► /api/analyze-frame | compare-people | camera-handoff ──► spawns Python scripts
```

**Why it's built this way:** the browser never talks to FastAPI directly. Next.js holds the session, and FastAPI trusts only requests that carry a shared secret.

- **`frontend/src/lib/pos-auth.ts`**: builds and checks an HMAC-SHA256 signed session cookie (`retailpulse-pos-session`, 8 h lifetime). It uses `timingSafeEqual` for the comparison and checks the role and expiry.
- **`api/auth/session`**: `GET` returns the current session. `POST` sends the login to FastAPI `/auth/login` and sets the cookie.
- **`api/auth/signup`**: accepts an invitation token through FastAPI `/auth/invitations/accept`, then sets the cookie.
- **`api/auth/logout`**: deletes the cookie.
- **`api/backend/[...path]`**: a generic proxy. It requires a valid session, removes the cookie and host headers, and adds `x-retailpulse-internal-secret`, `-role`, `-email` and `-user-id`.
- **`components/auth/AuthProvider.tsx`**: React context with `signIn`/`signOut`. It caches the role in localStorage so the UI shows the right state immediately on load.
- **`components/auth/RouteAccessGuard.tsx`**: client-side route gating.
  - Manager routes: `/dashboard`, `/customer-info`, `/employee-info`, `/spatial-analytics`, `/settings`, `/alerts`, `/voice-agent`.
  - Employee routes: `/employee-home`, `/my-performance`, `/employee`.
  - Shared: `/profile`.
- **Backend side (`backend/app.py`)**: the `require_internal`, `actor`, `require_manager` and `require_employee_or_manager` dependencies enforce the same roles again on the server.

## 3. Backend: store operations (`backend/app.py` and `backend/store_core.py`)

**Storage:** SQLite at `RETAILPULSE_DB_PATH`, with WAL mode and foreign keys on. The schema is created when the first connection opens.

**Tables:** `users`, `invitations`, `zones`, `cameras`, `rosters`, `settings` (JSON values), `alerts`, `orchestration_events`, `dispatch_decisions`, `tasks`, `task_events`.

**Seed data:**
- 6 zones: Entrance, 3 aisles, Promo, Checkout
- 3 cameras
- A demo manager and a demo employee (`password123`)
- One roster entry
- Default thresholds: response time, unattended wait, crowd %, dispatch timings and `dispatchPaused`
- 60-day retention
- One seed "Aisle 2 needs coverage" alert

**Passwords:** PBKDF2-SHA256 with 120k iterations and a per-user salt, compared in constant time.

**Accounts are invitation-only.** A manager creates a token valid for 7 days, and the invitee signs up with it.

### Endpoints

| Area | Endpoints | What they do |
|---|---|---|
| Auth | `POST /auth/login`, `/auth/invitations/accept` | Internal secret only, called by the Next.js auth routes |
| Settings | `GET /settings`; zones POST/PATCH; cameras POST/DELETE; rosters POST/PATCH; `PUT /settings/thresholds`, `/settings/privacy` | Manager-only CRUD; every call returns the full `settings_snapshot` |
| Accounts | `POST /accounts/invitations`, `PATCH /accounts/{id}` | Invite users; activate or deactivate them |
| Alerts | `GET /alerts?status=`, `POST /alerts/{id}/resolve` | Alert feed; resolving records who resolved it and when |
| Tasks | `GET /tasks/me`, `POST /tasks/dispatch`, `POST /tasks/{id}/transition`, `GET /tasks/events` (SSE stub) | Employees see and update only their own tasks |
| Orchestrator | `POST /orchestrator/events` | The decision engine (below) |
| Voice | `/voice-agent/status`, `/script`, `/speech`, `/generate` | LLM script, then text-to-speech |
| Status | `/health`, `/system-status` | Counts plus fixed worker states |
| Camera | mounted at `/camera` | The camera service (section 5) |

### How the orchestrator decides
`POST /orchestrator/events` handles one incoming event like this:

1. Logs the event.
2. Always creates an alert.
3. If dispatch is paused in settings, the decision is `paused`.
4. Otherwise, if the event type calls for dispatch (`unattended_customer`, `unstaffed_zone`, `crowding`), `select_dispatch_employee` picks an active, available employee with no open task. Employees rostered to the target zone come first.
5. If someone is found, it creates a task (state `delivered`, due in 30 s). If not, the decision is `no_eligible_employee`.
6. Writes a `dispatch_decisions` row recording the policy and the reason, so every decision can be audited.
7. If the request asks for it, also generates a voice script.

### Voice agent (`backend/voice_agent.py`)
- **Script:** sent to the Hugging Face router chat completions API with a calm 35–70-word staff-announcement prompt.
- **Audio:** ElevenLabs text-to-speech, returned as base64 MP3.
- **Fallbacks:** if `HF_TOKEN` is missing or the call fails, a deterministic template script is used. If ElevenLabs is missing or fails, the response is `audioBase64: null`. The feature never hard-fails.
- **Why stdlib `urllib`:** it avoids adding HTTP client dependencies.

## 4. Backend: standalone CV scripts (called by Next.js API routes)

Each script is spawned as a subprocess with `PYTHON_BIN`.

- **`analyze_frame.py`** (via `/api/analyze-frame`): reads a base64 JPEG on stdin and runs YOLOv8n person detection.
  - Role heuristic: the bottom 40% of the frame counts as customer, the top 60% as employee.
  - Scores interaction from the customer-to-employee ratio plus proximity under 150 px.
  - Status is one of `good` / `partial` / `unattended` / `idle` / `overwhelmed`.
  - This is an early prototype. The interaction module replaces it.
- **`compare_people.py`** (via `/api/compare-people`): counts people in two videos every Nth frame and returns a ratio verdict (`Balanced` / `V1 stronger ratio` / `V2 stronger ratio`). Writes JSON and CSV to `backend/output/`. The route caches results by video path and interval.
- **`video_similarity.py`**: compares two videos with SSIM and MSE at 300 random timestamps (seed 42). SSIM is implemented by hand, with no scikit-image dependency.
- **`vision_inference.py`**: shared `load_model` and `track_frame` helpers. It never downloads weights, caps torch threads, and runs ByteTrack.
- **`frontend/src/lib/dashboard-data.js`**: turns the committed `people_comparison.json` and `video_similarity.json` snapshots into the dashboard's summary numbers. Tested in `dashboard-data.test.js`.

## 5. Backend: two-camera handoff and global identity

The goal is to recognise the same person walking out of cam1 and into cam2 without face recognition.

- **`handoff_core.py`**: pure logic with no OpenCV, so it's testable on CPU (`test_handoff_core.py`).
  - Detects crossings of a vertical boundary (cam1 at x = 0.85 moving right, cam2 at x = 0.15 moving left).
  - Scores each candidate pair as `0.55 × appearance cosine + 0.45 × time compatibility`. Time compatibility is a triangle peaking at the midpoint of the allowed gap (1–45 s).
  - Matches pairs greedily one-to-one: ≥ 0.78 is `confirmed` and gets a `master-NNN` ID, ≥ 0.52 is `uncertain`, anything lower is `unmatched`.
- **`camera_handoff.py`**: runs YOLO + ByteTrack on each video (every 5th frame), records boundary events with a 2 s cooldown, and builds an appearance descriptor from the crop (HSV histograms 8/4/4 plus aspect and height ratios).
  - `attach_global_identities` merges identities only on confirmed Re-ID. Every other track gets its own global ID.
  - Customer-entry rules then promote people to the customer role.
  - Works both as a CLI and through `/api/camera-handoff`, which streams progress over SSE.
- **`camera_service.py`** (mounted at `/camera`): an async job API.
  - `POST /handoff` validates inputs. Videos must be inside the repo and have a video extension; boundaries are in 0–1; gaps must be sane.
  - `GET /jobs/{id}` returns job status.
  - `GET /people` and `GET /people/{id}` list global people.
  - `PUT /people/{id}/role` accepts only `employee` or `unknown`. Customer is deliberately never set by hand.
  - Protected by `x-camera-internal-secret`.
- **`interaction/identity.py`, `IdentityRegistry`**: binds each (session, camera, local track) to an anonymous `person-<uuid>`.
  - **Design rule:** appearance may link tracks, but it never decides role. Roles come only from manager registration or explicit `CustomerEntryRule` matches. Everyone else stays `unknown`.
  - Every role change writes a `role_assignment` audit record.
  - Backed by `interaction/storage.py`, a generic SQLite document store `(kind, store_id, id) → JSON`, or by an in-memory version.

## 6. Backend: the interaction module (`backend/interaction/`)

This is the main CV work, and the current branch. It decides when an employee is actually serving a customer. It is a standalone pipeline and is not yet connected to `app.py`.

### Pipeline A: practical video pipeline (`pipeline.InteractionPipeline`)
Runs this sequence on every frame:

1. **Detect and track** (`tracker.py`):
   - Model: the custom `best.pt` (employee/customer classes), exported to OpenVINO at 320 px. That runs at about 10 fps on a laptop CPU; on GPU the pipeline switches back to `.pt`.
   - Tracker: BoT-SORT with ReID (`botsort_reid.yaml`), so IDs don't swap when two people cross.
   - **ID relinking:** a person lost mid-frame (not at the left or right edge) is assumed to be hidden. A new ID that appears mid-frame within 5 s and has appearance similarity ≥ 0.90 gets the old ID back. A second pass folds a "young" ID back into the old one when the tracker spawned it during an occlusion.
2. **Role** (`role_classifier.py` and `cust_emp_classifier.py`): a weighted agent combines four signals.

   | Signal | Weight | Notes |
   |---|---|---|
   | YOLO role class | 0.55 | Signed: + for employee, − for customer |
   | HSV bib colour in the torso | 0.30 | Gets YOLO's weight too when YOLO has no opinion |
   | Staff-zone dwell | 0.10 | Only in configured staff-only zones |
   | Stationary time | 0.05 | Can never decide a role on its own |

   - The person is an employee when the score is ≥ 0.45.
   - The score is smoothed with an EMA (0.65). A role locks after holding for 3 s and only flips after the opposite role also holds for 3 s.
   - Aisle dwell time is intentionally not used as employee evidence, so a customer pausing to browse isn't misclassified.
3. **Proximity** (`engagement.py`): distance is measured in body heights, so it needs no floor calibration and tolerates a moving camera.
   - It compares the feet, hips or head bands, using the lowest band visible on both people. Thresholds are 1.0, 0.8 and 0.6 body heights.
   - A band is skipped if it's cut off by the frame edge or hidden behind someone nearer the camera.
   - Pairs whose heights differ by more than 0.6× are ignored, because they're at different depths.
   - **Pass-by filter:** if the customer's position relative to the employee drifts more than 0.5 body heights before 2 s have passed, the clock restarts. This rejects people walking past each other.
4. **Pose judge** (`pose.py`): a second-stage veto.
   - Runs `yolov8n-pose` on 4 crops of the pair from the last 2 s.
   - Confirms the interaction if someone's head (nose vs ear midpoint, or a single ear in profile) points at the other person's head within 60° in at least 50% of the frames.
   - Two people with their backs to the camera give no evidence and are rejected.
   - It runs inline (about 250 ms, once per candidate) because running it on a background thread made every frame about 2× slower.
   - A rejected pair is re-checked every 4 s.
   - If the judge fails, the result is `unverified` and proximity decides.
5. **Output:** `renderer.py` draws the boxes, body bands, interaction lines and an "INTERACTION: ON/OFF" badge.
   - `cli.py` writes the annotated `.mp4` plus `.detections.json`, `.people.json` (final role per ID, with role segments), `.interactions.json` and `.rejected_interactions.json`.
   - `--every` and `--track-every` decouple scoring from tracking: the tracker can run at 10 fps while roles are scored at 2 fps.
   - `service.py` is an optional single-frame FastAPI on port 8012.

### Pipeline B: "Track A" contract pipeline (`pipeline.FrameProcessor`)
A stricter, typed, production-shaped variant for a future events and storage layer ("Track B").

- **`cv_contracts.py`**: versioned Pydantic contracts: `TrackObservation`, `FrameResult`, `Signal`, `Orientation`, `Calibration`, `ModelVersion`. They check box geometry, unit-length facing vectors, session-namespaced track IDs and timezone-aware UTC.
- **`frames.py`**: decodes recordings with PyAV using the real presentation timestamps (no FPS-based timestamp guessing). It rejects missing or backward timestamps.
- **`live.py`**: an RTSP reader with a 1-slot latest-frame queue, reconnect backoff up to 30 s, and session start/end/error signals. It never logs the RTSP URL or credentials.
- **`core.py`**: deterministic logic. Point-in-polygon zones, cosine prototypes, head direction, `pair_qualifies` (distance plus mutual facing), and `EventEngine`, which turns pairs into engagement events with deterministic UUIDv5 IDs.
- **`geometry.py`**: IoU and Hungarian box matching (scipy), and zone lookup.
- **`calibration.py`**: few-shot appearance prototypes per camera. It's kept for wire compatibility only; appearance is explicitly not a role source.
- **`schemas.py`**: `CameraConfig`, `Zone`, `CustomerEntryRule`, `RoleAssignmentRequest`. All use strict validation with `extra="forbid"`.
- `process_recording` always emits exactly one start signal and one end signal per session. A failed frame comes back as `status="failed"`, never as an empty success.

### Benchmarking (`benchmark.py`, `benchmarks/`)
- Detector KPIs via Ultralytics `val` on the held-out split.
- Interaction precision, recall and F1 by temporal-IoU matching against annotated intervals, measured both with and without the judge.
- Speed: realtime factor, p50/p95 frame latency, per-stage timings (track, classify, judge, decode), and a track-ID count as a proxy for ID fragmentation.
- `--only` runs a subset of videos; `--label` appends a row to `benchmarks/speed_log.csv`.
- **Spec (`benchmarks/benchmark.json`):** 11 clips from `dummydataset/` (gitignored `.MOV` files, sampled with `every`/`track_every` = 10), a `temporal_iou` of 0.5 and the detector's held-out split at `~/data/split/test` (outside the repo).
  - Only `IMG_8829` has reviewed interaction intervals, and that clip is in the detector's **training** split, so it's valid for interaction KPIs only.
  - The other 10 carry `candidates_to_review` (pipeline output awaiting a human verdict). Until someone moves them into `interactions`, they count for speed only.
- Run: `python -m backend.interaction.benchmark backend/interaction/benchmarks/benchmark.json [--judge off] [--skip-detector] [--only IMG_8881] [--label name]`.
- `report.json` currently (uncommitted re-run) shows:
  - Detector: mAP50 0.969 and mAP50-95 0.896 on 455 images (precision 0.963, recall 0.953), about 60 ms per image. Customer recall (0.916) is the weakest class figure; employee recall is 0.990.
  - Interactions: the judge took F1 from 0.67 to 1.0 by removing the one false positive. That's measured on only **one labelled video**, so it's thin evidence.
  - Speed: every clip now runs faster than realtime; the worst (`IMG_8881`) is 1.25×. Decode takes 12–26 s per clip, a large share of wall time.
- `speed_log.csv` (untracked) holds one row per labelled run (`baseline`: 11 videos, worst 1.25×, p50 128 ms / p95 361 ms, track 156 ms, judge 369 ms, 55 track IDs in total).
- **Uncommitted work on this branch:** `benchmark.py` gained the per-stage timers (`timed()` wraps `detect_and_track`, `classify` and the judge's `classify_interaction`), `decode_s`, `people_per_frame_mean`, the `track_ids` count, `--only`, `--label` and `log_row()`, with a matching test in `test_benchmark.py`.

## 9. Gaps worth knowing
0. **Live API keys in git history:** `.env.example` at `HEAD` (since commit `d3a9850`, pushed to `origin`) contains a real `HF_TOKEN` and `ELEVENLABS_API_KEY`. The uncommitted change blanks them, but they stay in history. Revoke and rotate both keys; blanking the file isn't enough.
1. **Unguarded CV routes:** `/api/analyze-frame`, `/api/compare-people` and `/api/camera-handoff` have no session check. `camera-handoff` also accepts any absolute file path.
2. **Client-only page guard:** `RouteAccessGuard` runs only in the browser; there's no `middleware.ts`. The backend APIs are still role-checked, so data is protected, but pages aren't gated server-side.
3. **Session secret name mismatch:** `.env.example` sets `POS_AUTH_SECRET`, but `pos-auth.ts` reads `POS_SESSION_SECRET` or `NEXTAUTH_SECRET`. Sessions are therefore signed with the hard-coded default.
4. **Wrong demo password in docs:** the `.env.example` comment says the manager password is `123456`, but the seeded value is `password123`.
5. **Camera service unreachable through the proxy:** it expects `x-camera-internal-secret` (default `local-dev-camera-secret`, not in `.env.example`), and the proxy doesn't send that header.
6. **Stubs and hard-coded values:**
   - `/tasks/events` SSE sends only a single "ready" event.
   - `/system-status` worker states are hard-coded.
   - The navbar alert badge always says "5".
7. **Interaction module not connected:** it doesn't feed `/orchestrator/events` yet, so alerts and dispatch are only triggered manually.
8. **Test command:** `test_handoff_core.py` must be run from inside `backend/`. Running pytest from the repo root fails on an import.
9. **Fresh clone can't run the demo:** the videos the dashboard, handoff and benchmark need are all gitignored, and the detector test split lives at `~/data/split/test`, outside the repo.
10. **Benchmark labels:** 10 of the 11 benchmark clips still wait for interaction review, so interaction precision and recall rest on one clip.
